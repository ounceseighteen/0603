Аудит проекта «Мир Кино» по OWASP Top 10:2025
Ниже — построчный разбор по всем десяти категориям, а также отдельно по legacy-коду и разбиению модулей. По каждой категории — вердикт (нашел / проверил / чисто / не применимо) и находки в требуемом формате.

A01 — Контроль доступа (Broken Access Control)
Вердикт: нашел

Находка A01-1. @login_required не различает роли на пользовательских маршрутах
Файл и строка: public.py, @public_bp.route('/book', methods=['POST']) → def book(): (строка с @login_required над book), а также cabinet.py api_ticket (строка с декоратором @login_required), cabinet.py cancel_booking (строка @cabinet_bp.route('/cancel_booking/<int:booking_id>', methods=['POST']) + @login_required).

Что даёт злоумышленник на вход: логинится как cashier (роль есть в системе, см. security.ALLOWED_ROLES и seed_db, где создаётся cashier@demo.ru). Затем вызывает POST /cancel_booking/<id> для чужой брони или POST /book (или POST /client/book из staff.py).

Что получает на выходе: cancel_booking проверяет роль только внутри if-ветки:

python
if user['role'] in ('admin', 'cashier'):
    booking = conn.execute('SELECT * FROM bookings WHERE id=?', ...)
else:
    booking = ... WHERE id=? AND user_id=? ...
То есть кассир может отменить любую бронь. А book() в public.py вообще не проверяет роль — кассир/админ может создавать себе брони как клиент, обходя бизнес-правила (например, лимиты). api_ticket для не-клиента тоже отдаёт любой билет по id без проверки владельца (ветка else в cabinet.py):

python
if user['role'] == 'client':
    row = ... WHERE b.id=? AND b.user_id=?
else:
    row = ... WHERE b.id=?
Насколько опасно: средне-высоко. Роль cashier задумана как «продажа на кассе», а не «чтение любых билетов и отмена чужих броней без ограничения сценария». Плюс любой сотрудник может действовать как клиент. Для полноценного IDOR клиента нет (там есть AND b.user_id=?), но модель ролей нарушена.

Находка A01-2. admin_user_role/admin_user_ban — админ может разжаловать/забанить другого админа, кроме себя
Файл и строка: admin.py, @admin_bp.route('/admin/users/ban/<int:user_id>', methods=['POST']) → def admin_user_ban(...): проверка if user['id'] == user_id: return redirect(...); аналогично admin_user_role.

Что даёт злоумышленник на вход: скомпрометированный аккаунт admin отправляет POST на /admin/users/role/<other_admin_id> с role=cashier.

Что получает на выходе: роль второго администратора понижается. Единственная защита — «нельзя себе». При наличии двух админов один может «съесть» другого.

Насколько опасно: средне. Это не эскалация прав, но ослабление контроля: скомпрометированный админ может нейтрализовать второго админа.

Находка A01-3. admin_hall_delete/admin_film_delete/admin_session_delete — разрушительные операции без подтверждения паролем/2FA
Файл и строка: admin.py, функции admin_film_delete (строка с @admin_bp.route('/admin/films/delete/<int:film_id>', methods=['POST'])), admin_hall_delete, admin_session_delete.

Что даёт злоумышленник на вход: скомпрометированная админ-сессия (или CSRF-запрос, см. A01-4) — POST на /admin/films/delete/1.

Что получает на выходе: каскадное удаление фильма, всех его сеансов, броней и истории бонусов (DELETE FROM bonus_history WHERE booking_id IN (...)).

Насколько опасно: высоко по последствиям (потеря данных, необратимо), но это не уязвимость per se, а небезопасный дизайн (см. A06). Регистрирую как находку по A01, потому что проверка «а точно ли это тот админ» отсутствует.

Находка A01-4. Все административные POST-маршруты защищены только CSRF, но ALL_ADMIN_ENDPOINTS не снимает проверку CSRF для fetch
Файл и строка: base.js, IIFE в начале файла, window.fetch = function (input, init) { ... if (!init.headers.has('X-CSRFToken')) init.headers.set('X-CSRFToken', CSRF_TOKEN); ... }.

Что даёт злоумышленник на вход: сторонний сайт шлёт fetch('/admin/films/delete/1', {method:'POST'}) — без CSRF-токена.

Что получает на выходе: Flask-WTF CSRFProtect вернёт 400. Но: если жертва-админ сама зайдёт на страницу злоумышленника, тот может открыть <form action="https://mirkino/admin/films/delete/1" method="POST"> и автоподставить token не сможет — токен привязан к сессии жертвы, а злоумышленник его не знает. То есть CSRF-защита работает.

Насколько опасно: не опасно. Но есть отдельный нюанс: MutationObserver в base.js вставляет csrf_token во все формы, включая формы, отправляемые на другие origin (если такие появятся). Сейчас таких нет. Проверено.

A02 — Настройка по умолчанию (Security Misconfiguration)
Вердикт: нашел

Находка A02-1. Админ создаётся при первом запуске с паролем из окружения, но SEED_DEMO_DATA=1 создаёт клиентов с одинаковым паролем
Файл и строка: db.py, seed_db, строка demo_password = os.environ.get('DEMO_PASSWORD', 'DemoPass123!') и _add_user(...) для anna@demo.ru, ivan@demo.ru, olga@demo.ru, dmitry@demo.ru, elena@demo.ru, cashier@demo.ru.

Что даёт злоумышленник на вход: знает, что демо-данные включены (например, найден .env.example/README), пробует anna@demo.ru / DemoPass123!.

Что получает на выходе: вход в клиентский аккаунт с ненулевым бонусным балансом (у Ольги — 18750 бонусов, у Анны — 4200, у Дмитрия — 3500).

Насколько опасно: критично, если SEED_DEMO_DATA=1 остался в проде. По умолчанию переменная не задана, поэтому защита — «на честном слове администратора». Нет автоматической проверки «а не прод ли это».

Находка A02-2. SECRET_KEY обязателен, но нет валидации «не дефолтный»
Файл и строка: config.py, строка SECRET_KEY = require_env('SECRET_KEY').

Что даёт злоумышленник на вход: ничего — если админ поставил SECRET_KEY=changeme (частая практика при копировании .env.example).

Что получает на выходе: полный контроль над сессиями (подделка cookie session), включая админские, если не включён SESSION_COOKIE_SECURE и не проверяется IP.

Насколько опасно: критично. Нет проверки длины/энтропии/«это не из примера». Проверка len(SECRET_KEY) < 32 и запрет строки changeme/secret отсутствует.

Находка A02-3. Отладочный режим: FLASK_DEBUG=1 включает Werkzeug-консоль
Файл и строка: main.py, app.run(debug=config.DEBUG, ...); config.py, DEBUG = os.environ.get('FLASK_DEBUG') == '1'.

Что даёт злоумышленник на вход: если админ поставил FLASK_DEBUG=1 (в комментарии сказано «включить локально и сознательно»), злоумышленник открывает /console.

Что получает на выходе: интерактивный Python-шелл в процессе сервера (если угадает PIN, который печатается в консоль). Это полный захват сервера.

Насколько опасно: критично. Комментарий в main.py предупреждает, но никак не блокирует. Нет проверки «если не 127.0.0.1 — не запускаться с debug».

Находка A02-4. CSP разрешает 'unsafe-inline' и 'unsafe-eval'
Файл и строка: security.py, set_security_headers, строка:

python
"script-src 'self' 'unsafe-inline' 'unsafe-eval'; ..."
Что даёт злоумышленник на вход: любая XSS-точка (например, инъекция в title фильма, который попадает в onclick="..." в шаблоне) — и unsafe-inline пропустит инлайн-скрипт.

Что получает на выходе: исполнение JS в контексте сайта, угон сессии, CSRF-токенов.

Насколько опасно: средне-высоко. CSP в текущем виде почти не защищает от XSS. Для проекта с инлайн-скриптами в шаблонах это компромисс, но unsafe-eval не нужен почти никогда.

A02-5. SESSION_COOKIE_SECURE по умолчанию выключен
Файл и строка: config.py, строка SESSION_COOKIE_SECURE = os.environ.get('FORCE_HTTPS') == '1'.

Что даёт злоумышленник на вход: пассивный слушатель в той же сети (Wi-Fi кафе) ждёт HTTP-запрос.

Что получает на выходе: cookie session в открытом виде → угон сессии.

Насколько опасно: высоко, если прод работает по HTTP. В коде нет принудительного редиректа на HTTPS (нет ProxyFix, нет before_request, проверяющего request.is_secure).

A02-6. MAX_CONTENT_LENGTH = 8 МБ, но save_uploaded_image дополнительно проверяет 5 МБ
Файл и строка: config.py, MAX_CONTENT_LENGTH = 8 * 1024 * 1024; utils.py, save_uploaded_image, if len(raw) > 5 * 1024 * 1024.

Что даёт злоумышленник на вход: файл 7 МБ.

Что получает на выходе: Flask примет запрос (8 МБ), save_uploaded_image отклонит (5 МБ). Работает.

Насколько опасно: не опасно. Проверено.

A03 — Цепочка поставок и чужие зависимости (Software Supply Chain Failures)
Вердикт: проверил

A03-1. requirements.txt в проекте отсутствует
Файл и строка: в присланных файлах нет requirements.txt, pyproject.toml, Pipfile. Импортируются: flask, flask_mail, flask_wtf, flask_limiter, qrcode, PIL, werkzeug, dotenv.

Что даёт злоумышленник на вход: ничего — это отсутствие файла.

Что получает на выходе: невозможно воспроизвести окружение, невозможно проверить версии на известные CVE, невозможно зафиксировать хэши.

Насколько опасно: средне. Без lock-файла pip install flask через год поставит другую версию, и поведение/уязвимости изменятся. Нет pip-audit/safety в CI.

A03-2. qrcode и Pillow опциональны, но проверка ImportError тихая
Файл и строка: mailer.py, try: import qrcode ... except ImportError: QR_AVAILABLE = False; print('ВНИМАНИЕ: ...'); cabinet.py, try: import qrcode as _qrcode; QR_AVAILABLE = True except ImportError: QR_AVAILABLE = False.

Что даёт злоумышленник на вход: ничего.

Что получает на выходе: если qrcode не установлен, билеты уходят без QR — но пользователь этого не видит. Это не безопасность, а надёжность.

Насколько опасно: низко.

A03-3. import secrets, import hashlib — стандартная библиотека, ок
Файл и строка: utils.py, generate_loyalty_card_number, create_verification_code — используется secrets.randbelow. Это корректно.

Насколько опасно: не опасно. Чисто для генерации кодов.

A03-4. werkzeug.security.generate_password_hash без указания метода
Файл и строка: db.py, hash_password: return generate_password_hash(password).

Что даёт злоумышленник на вход: ничего.

Что получает на выходе: Werkzeug сам выберет метод по умолчанию — в новых версиях это scrypt, в старых — pbkdf2:sha256. Дефолт меняется между версиями, а старые хэши остаются валидными (Werkzeug хранит метод в строке хэша). Проблема: если в проекте окажется очень старая версия Werkzeug, метод может быть слабым.

Насколько опасно: низко-средне. Явное method='scrypt' было бы надёжнее.

A03 — что нельзя проверить чтением кода
Версии всех зависимостей (нет lock-файла).

Наличие CVE в конкретных версиях Flask/Werkzeug/Pillow.

Наличие проверки целостности пакетов (hash checking) в CI.

A04 — Криптография и секреты (Cryptographic Failures)
Вердикт: нашел

Находка A04-1. Legacy-пароли в виде сырого SHA-256 без соли
Файл и строка: db.py, verify_password:

python
if stored_hash and re.fullmatch(r'[0-9a-f]{64}', stored_hash or ''):
    import hashlib as _hashlib
    return _hashlib.sha256(password.encode()).hexdigest() == stored_hash
и upgrade_password_hash_if_needed.

Что даёт злоумышленник на вход: получает дамп БД (например, через SQL-инъекцию или бэкап). Находит пользователей со старыми хэшами.

Что получает на выходе: SHA-256 без соли → мгновенный перебор по rainbow-таблицам; одинаковые пароли дают одинаковые хэши.

Насколько опасно: высоко. Легаси-совместимость — временная мера, но она остаётся в коде навсегда и не помечена сроком. Плюс: при входе хэш обновляется, но пользователи, которые не заходят, остаются уязвимыми.

Находка A04-2. hash_password используется и для паролей, и для кодов подтверждения
Файл и строка: utils.py, create_verification_code: hash_password(code); check_verification_code: check_password_hash(row['code_hash'], input_code).

Что даёт злоумышленник на вход: ничего.

Что получает на выходе: для 6-значного кода scrypt/pbkdf2 — избыточно, но не вредно. Однако max_attempts=5 — это уже правильная защита от перебора.

Насколько опасно: не опасно. Чисто (с оговоркой про производительность: scrypt на каждый ввод 6-значного кода — это CPU-нагрузка; при 5 попытках не критично).

Находка A04-3. SECRET_KEY может быть коротким, хардкод отсутствует
Файл и строка: config.py, SECRET_KEY = require_env('SECRET_KEY').

Что даёт злоумышленник на вход: если админ поставил SECRET_KEY=123, злоумышленник может перебрать/угадать.

Что получает на выходе: подделка Flask-сессии, включая user_id админа.

Насколько опасно: высоко. В коде нет проверки длины. Рекомендуется if len(SECRET_KEY) < 32: raise RuntimeError(...).

Находка A04-4. Бонусная карта: номер генерируется secrets.randbelow, но не проверяется на коллизии при вставке
Файл и строка: utils.py, generate_loyalty_card_number: цикл while True: ... if not existing: return card_number.

Что даёт злоумышленник на вход: ничего.

Что получает на выходе: цикл защищает от коллизий в рамках одного соединения, но при параллельной генерации двух карт возможна гонка: оба потока увидят «свободно», оба вставят → UNIQUE constraint на card_number бросит IntegrityError, и запрос упадёт.

Насколько опасно: низко (вероятность коллизии 12-значного числа ~0, и падение обрабатывается Flask-ом как 500). Не критично.

Находка A04-5. log_audit пишет IP, но не пишет, был ли запрос по HTTPS
Файл и строка: db.py, log_audit: request.remote_addr or ''.

Что даёт злоумышленник на вход: ничего.

Что получает на выходе: при работе за reverse-proxy remote_addr — это IP прокси, а не клиента. Нет ProxyFix, нет X-Forwarded-For.

Насколько опасно: низко (для аудита), но снижает ценность журнала при расследовании.

A04 — что нельзя проверить чтением кода
Энтропию реального SECRET_KEY в проде.

Наличие TLS на периметре.

Как именно хранятся .env и бэкапы БД.

A05 — Инъекции (SQL, команды, HTML)
Вердикт: нашел

Находка A05-1. f-строка в SQL с плейсхолдерами (не инъекция, но требует внимания)
Файл и строка: api.py, api_notifications_read:

python
marks = ','.join('?' for _ in ids)
conn.execute(f'UPDATE notifications SET read=1 WHERE user_id=? AND id IN ({marks})', [user['id']] + [int(i) for i in ids])
и cabinet.py, api_ticket, mailer.py, send_paid_tickets_email: placeholders = ','.join('?' for _ in booking_ids) → f"""... WHERE b.id IN ({placeholders}) ...""".

Что даёт злоумышленник на вход: список ids / booking_ids.

Что получает на выходе: сами значения идут через ?, а f-строка вставляет только ?. Инъекции нет. Но: если в ids попадёт не-int (в api_notifications_read есть int(i) — ок; в mailer.send_paid_tickets_email есть booking_ids = [int(x) for x in booking_ids if x] — ок; в api_ticket — один ?).

Насколько опасно: не опасно. Чисто по инъекциям, но паттерн «f-строка для генерации плейсхолдеров» опасен тем, что при рефакторинге кто-то вставит туда значение.

Находка A05-4. XSS через title фильма в onclick-атрибутах шаблонов
Файл и строка: шаблоны не присланы, но в base.js есть:

js
const notif = JSON.stringify({ link: n.link || '', booking_id: n.booking_id || '' })
    .replace(/"/g, '&quot;').replace(/'/g, '&#39;');
...
'<div class="notif-item..." onclick="openNotif(' + n.id + ', ' + notif + ')">'
и в shop.js:

js
btn.innerHTML = `<span ...>${s.time}</span><br><span ...>${s.price} ₽</span>`;
где s.time, s.price приходят из /api/film/<id> (сервер их не экранирует, но они из БД).

Что даёт злоумышленник на вход: если админ через форму добавит фильм с названием "><script>fetch('/admin/users/role/1',{method:'POST',body:...})</script>, то в шаблонах, где title вставляется в onclick="openFilmModal(<id>)" без экранирования, сработает XSS. Насколько опасно: высоко, если шаблоны вставляют пользовательские данные без экранирования. В присланных .js файлах escapeHtml есть только в base.js. Это потенциальная находка, требующая проверки шаблонов (их нет в присланных файлах).

Находка A05-5. SQL-инъекция через session_id в sell_ticket/client_book — параметры идут через ?
